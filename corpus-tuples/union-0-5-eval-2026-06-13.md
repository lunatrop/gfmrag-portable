# 0-5 union build + graph-vs-flat A/B (2026-06-13)

Full-corpus union of all six shards, and an A/B that compares GFM-RAG graph
retrieval against a flat semantic baseline over the same embeddings.

## Build

- **shard-5 stage-1:** 17 sub-shards `s5-0..16` (au-register profile), SA-driven
  campaign, ~86% mean fact-gate, all stage-1 on the bucket.
- **Merges (method-3 exact-name dedup, 0 dangling edges):**
  - shard-5: 50,664 nodes · 1,353,372 edges · 11,634 docs
  - **union-0-5: 67,144 nodes · 1,964,489 edges · 17,090 docs** (14,946 cross-shard dups collapsed)
- **Stage-2 on the QA L4 — recipe that worked:**
  `DATA_NAME=<ds>, GFMRAG_EMB_BATCH_SIZE=4, PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`.
  - batch-16 CUDA-OOM'd the L4 on 50k+ long-document-text nodes; **batch-4** fits.
  - The QA **Service** builds stage-2 under a 35-min startup probe; embedding
    67k nodes + ColBERT warmup exceeds it, so the first revision fails the probe
    **but graph.pt persists** (written ~25min, before the deadline). **Re-trigger**
    (bump a dummy env var) → next cold-start loads the prebuilt graph + rebuilds
    ColBERT (~18min) → passes. union graph.pt = ~419MB, serving (rev 00023).
  - First query triggers a one-time ColBERT build over 67k entities (~14min),
    then ~1s; the index is ephemeral (`/tmp`), rebuilt each cold-start.

## A/B: graph vs flat (12 queries, `tmp`→`scripts/eval/run_ab.py`)

- **GRAPH:** GFM-RAG `/retrieve`, `target_types=["document"]`.
- **FLAT:** cosine top-k over the **same** document-node embeddings extracted
  from `graph.pt` (identical Qwen3-Embedding space) — isolates only the retrieval
  algorithm.

**Result: flat beats graph on all 11 substantive queries (top-5 overlap 0/5;
control "IKEA ABN" 4/5).** On sector queries the flat hits are on-target
(mining→mining, apparel→apparel, food→food); the graph results are dominated by a
few recurring hub nodes — `CONTRACT POWER ASSETS …`, `UNITED MALT GROUP …` appear
in the graph top-5 of nearly every unrelated query.

## Diagnosis (working hypothesis, not yet confirmed)

Hub-node domination. Caveats that lower confidence in the "drop `equivalent`
edges" fix:
- The visible hubs are **document** nodes (joint/group statements), whose degree
  comes from many *legitimate* entity connections (co-filers, ABNs, sectors) —
  **not** from `equivalent` (entity↔entity synonym) edges. So dropping
  `equivalent` edges may not reduce the *document* hubs.
- These are broad sector/keyword queries — flat's home turf; not a true multi-hop
  test (named-entity → relationships).

**Pending diagnostics (read-only):** (1) degree-composition of the dominating
nodes (equivalent vs legit), (2) determinism re-run, (3) true relational queries.
Only if these confirm the hypothesis should the hub-suppression rebuild run —
under a **new dataset name** (`union-0-5-nohub`) so `union-0-5` stays revertable.
