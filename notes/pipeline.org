* Infrastructure (the decided options)

- *Platform: Cloud Run* (=deploy/cloudrun/=) — won the Cloud-Run-vs-GKE
  evaluation. Scale-to-zero means idle cost ≈ A$0 (storage only) vs the GKE
  stack's ~A$975/mo floor; L4s without zonal redundancy are granted on demand
  (no quota request needed). The GKE stack (=deploy/terraform/=) remains as
  the alternative for sustained/queue-depth workloads.
- *Region: us-central1.* Sydney evaluated and deferred — australia-southeast1
  has no L4s (T4/P4/P100/H100 only) and no Cloud Run GPUs at all. Revisit if
  non-public AU data enters the corpus or L4s reach Sydney.
- *Components:* =gfmrag-vllm= service (OpenAI-compatible /v1),
  =gfmrag-extract= job (CUDA-devel image: ColBERT PLAID JIT-compiles at
  runtime; faiss-gpu; 1h task timeout), =gfmrag-qa= service (gated behind
  =qa_enabled= until an index exists). Images built by Cloud Build
  (=deploy/cloudbuild/=), Docker Hub via AR remote proxy.
- *Costs (live AUD catalog rates):* L4 node ≈ A$1.2–1.6/hr active; full
  17k-doc corpus extraction estimated ≈ A$10–20; shard-0 test runs cost
  single-digit AUD including failures.

* Stage 1 — raw corpora → shards

=scripts/prepare_corpus_shards.py= renders each register CSV row into the
passage format validated in the smoke test (entities with "(ABN …)" labels,
period, HQ, revenue band, sectors, included entities, register link) and
writes =corpus-shards/shard-N/raw/documents.json=. 17,226 rows → 17,090 docs
(136 skipped: no reporting entities).

** Sharding options (tied to extraction infra)
| Mode        | Flag                                           | Use                   | Infra mapping                                                             |
|-------------+------------------------------------------------+-----------------------+---------------------------------------------------------------------------|
| equal       | =--shards N= (default 4)                       | production extraction | one shard per parallel job task; task index = shard index; wall-clock ÷ N |
| exponential | =--mode exponential= / =--ladder 16,64,…,rest= | cost measurement      | run rungs in order, extrapolate cost/doc before committing the big rung   |

Both are deterministic (=--seed=, default 42); ladder mode shuffles first so
small rungs are representative (the CSV is ordered by year). Rungs are
disjoint — the measurement runs *are* the production run.

** Quality gates at this stage
- Converter idempotency: same seed → byte-identical shards.
- Row accounting: docs out + skipped = rows in (17,090 + 136 = 17,226).
- Text warts: the stray-paren bug (=GME PTY LTD.)=) was found via rung-0
  output review and fixed; 709 → 244 =X.)= occurrences (remainder are genuine
  names). Known residual: ABN-less entity followed by a comma cannot be split
  from its neighbour.
- *Goal:* shards faithfully and deterministically represent the register, so
  every downstream error is attributable to extraction, not input.

* Stage 2 — NER + tuple extraction

Two LLM calls per document (NER, then OpenIE triples) against an
OpenAI-protocol endpoint; identical gfmrag code local and cloud, only
=llm_api= + endpoint differ.

** Extraction prompts

Source of truth: =gfmrag/graph_index_construction/openie_extraction_instructions.py=
(message templates =ner_prompts= and =openie_post_ner_prompts=; consumed by
=gfmrag/graph_index_construction/ner_model/llm_ner_model.py= and
=openie_model/llm_openie_model.py=).

Each call = system instruction + ONE generic one-shot example + the document.

*Call 1 — NER system instruction* (=ner_instruction=):
#+begin_example
Your task is to extract named entities from the given paragraph.
Respond with a JSON list of entities.
Strictly follow the required JSON format.
#+end_example

User-turn frame (=ner_user_input=): =Paragraph:```\n{user_input}\n```=

*Call 2 — OpenIE system instruction* (=openie_post_ner_instruction=):
#+begin_example
Your task is to construct an RDF (Resource Description Framework) graph from the given passages and named entity lists.
Respond with a JSON list of triples, with each triple representing a relationship in the RDF graph.

Pay attention to the following requirements:
- Each triple should contain at least one, but preferably two, of the named entities in the list for each passage.
- Clearly resolve pronouns to their specific names to maintain clarity.
#+end_example

Your task is to construct an RDF (Resource Description Framework) graph from the given passages and named entity lists.
Respond with a JSON list of triples, with each triple representing a relationship in the RDF graph.

Pay attention to the following requirements:
- Each triple should contain at least one, but preferably two, of the named entities in the list for each passage.
- Every identification number (e.g. ABN) must appear in exactly one triple: [entity, "has ABN", number]. Output these triples first.
- When several entities act jointly, create the relationship triple for each pair in both directions, and repeat shared attributes (period, headquarters, revenue, sectors) for EVERY entity.
- Clearly resolve pronouns to their specific names to maintain clarity.

User-turn frame (=openie_post_ner_frame=) — receives the passage plus call
1's entity JSON:
#+begin_example
Convert the paragraph into a JSON dict, it has a named entity list and a triple list.
Paragraph:
```
{passage}
```

{named_entity_json}
#+end_example

The example is completely generic — and that explains the fact-gate findings
directly:

- *ABN recall 41–56%*: the example contains NO identifiers, so there is no
  pattern for ="has ABN"= triples; entity-dense joint statements shed the
  parenthetical ABNs first.
- *Fragmented relations* (=filed= / =with= / =for= as separate relations):
  the example's relations are short verb phrases; the model mirrors that
  granularity.
- *Why 7B didn't beat 3B in the A/B*: both work from the same
  under-specified instruction — extra capacity went into paraphrase, not
  completeness.

*Planned fix (the ABN lever)*: replace/augment the one-shot with a
register-style example — one joint statement demonstrating ="has ABN"=
triples, co-filer triples in both directions, and a canonical relation
vocabulary (=filed joint statement with=, =operates in sector=, …). One-file
edit; re-extract a rung and let =verify_tuples.py= measure the delta against
the 41% baseline. Prompt work, not parameters.

** Model options for tuple extraction
| Option | Where | Status | Notes |
|--------+-------+--------+-------|
| qwen2.5:3b (Ollama) | local | *default, validated* | 89% clean triples on register text; ~87 s/doc on the 960M; hydra profiles =openie_model=ollama_qwen= |
| Qwen2.5-3B-Instruct (vLLM) | cloud | *deployed, validated* | first cloud extraction ran this; fits L4 comfortably, fastest cold start |
| Qwen2.5-7B-Instruct (vLLM) | cloud | option (one tfvars line) | accuracy leader in local benchmarks (16 ent/13 trip vs 11/10); recommended once cost ladder confirms budget |
| gemma2:2b (Ollama) | local | alternate, NER only | best small-model entity recall but emits 0 triples on register text — kept as NER-strong fallback |

Same-family principle: local 3B ↔ cloud 3B/7B are all Qwen2.5, so prompt
behaviour and output format validated locally transfer to the cloud. Caveat:
Ollama serves 4-bit quants — local validates *format/behaviour*, not exact
output.

** Guided decoding
vLLM's =--guided-decoding-backend outlines= forces valid JSON triple arrays.
Local rung-0 malformed-arity rate (11%) is the baseline this must beat —
target ~0% on cloud rungs. Guided decoding fixes *shape*, not *truth* (see
genre risk below).

** Quality gates at this stage
- Per-doc success: non-empty entities AND triples for every doc (rung gate).
- Arity rate: % of triples that are not clean 3-tuples — tracked per rung in
  =corpus-tuples/ladder-results.md=.
- *Fact-verification gate* (=scripts/verify_tuples.py=): because the corpus
  derives from structured CSV, ground truth is free. Verifies entity names,
  ABNs, revenue band, period, HQ, sectors against the register; flags
  entity-like nodes matching NO register entity (the =WOOLWOOLHHS= LLM-typo
  class). Required before any lead-gen use.
- Genre risk (documented failure): discursive/opinion text (LinkedIn post
  test) produced 67% arity failures and a *wrong-object hallucination*
  (KPMG events bound to Arthur Andersen's 2002). Mitigations for future
  news/commentary corpora: sentence-level chunking, 7B model, and the
  verification gate. Keep an opinion-style doc in the golden set.
- *Goal:* every triple admitted to the KG is well-formed and traceable to a
  source fact; malformed or unverifiable triples never reach stage 3.

* Stage 3 — KG construction & embedding

=KGConstructor= assembles stage-1 output: entity linking over node names
(ColBERT v2, GPU; PLAID index JIT-compiles CUDA at runtime — the reason for
the CUDA-devel image) and cosine-similarity synonym edges
(=BAAI/bge-large-en-v1.5=, threshold 0.8). Output per shard:
=nodes.csv / edges.csv / relations.csv= (shard-0: 126/638/46).

** Embedding options — pinned by the chosen reasoner
The stage-2 build is *not interchangeable* between checkpoints; each
checkpoint's config pins its embedder, dimension and dataset class:

| Checkpoint | Embedder | Dim | Dataset class |
|-----------+----------+-----+---------------|
| GFM-RAG-8M (32 MB) | sentence-transformers/all-mpnet-base-v2 | 768 | GraphIndexDatasetV1 |
| G-reasoner-34M (133 MB) | Qwen3-Embedding-0.6B (=truncate_dim=1024=) | 1024 | GraphIndexDataset (node features ON) |

Critical rule: the SAME embedder is used twice — stage-2 index build and
per-query encoding at serving time. Mismatch = silent garbage retrieval.
An ST (sentence-transformers) fallback for the Qwen3 embedder
(=gfmrag/text_emb_models/qwen3_model.py=) allows vLLM-free local builds.

** Quality gates at this stage
- Entity-resolution integrity: surface variants (case, suffixes, typos) merge
  to single nodes — spot-check known entities; fragmentation silently
  destroys multi-hop reasoning.
- Graph sanity: no orphan edges; node count ≥ unique register entities for
  full-corpus runs.
- Embedder/checkpoint consistency check at QA startup (dimension mismatch
  must fail loudly, not degrade silently).
- *Goal:* one well-connected graph per corpus where every node is a real,
  deduplicated register entity or extracted concept.

* Stage 4 — reasoner choice: DECIDED — G-reasoner-34M MUST be used

*Requirement (2026-06-11): production serving uses =rmanluo/G-reasoner-34M=.*
Pinned as the =gfm_model_path= default in =deploy/cloudrun/terraform.tfvars=;
8M is retained ONLY as the A/B control for eval reruns, never for serving.

Decided by the shard-0 cloud eval (49 CSV-derived questions, gold answers
from the register — =corpus-tuples/shard-0/qa-eval-{8M,34M}.json=):

|                 | GFM-RAG-8M                                            | G-reasoner-34M                                    |
|-----------------+-------------------------------------------------------+---------------------------------------------------|
| retrieval hit@5 | 82% (40/49)                                           | *98% (48/49)*                                     |
| answer accuracy | 82% (40/49)                                           | *98% (48/49)*                                     |
| failure pattern | systematic: 8/9 misses are reporting-period queries   | one miss (a2 Milk multi-hop, which 8M also fails) |
| checkpoint      | 32 MB                                                 | 133 MB                                            |
| serving cost    | ≈ identical (the GNN is the cheapest part of the pod) |                                                   |
| stage-2 build   | mpnet/768/V1                                          | Qwen3-0.6B/1024/node-features                     |

The gap is statistically real (all 8 discordant questions favour 34M,
p < 0.01) at identical serving cost — there is no trade-off to weigh.
Caveats on record: the eval demonstrates single-fact retrieval robustness,
not yet the multi-hop advantage (the only true multi-hop question fails on
both — add =RelatedStatements=-derived multi-hop questions); and scale is
small (16 docs) — re-run =qa_eval.py= per ladder rung to confirm the gap
holds as the graph grows.

Operational note: each checkpoint's stage-2 build persists in the bucket
under its own fingerprint (rw data mount), so 8M↔34M swaps for A/B reruns
are cheap; the first deployment of a checkpoint pays its stage-2 build once.

* Stage 5 — serving & usage

=gfmrag-qa= (Cloud Run, own L4, =qa_enabled=true= once an index exists in
GCS). Per request: query NER (→vLLM) → entity linking (ColBERT) → query
embedding (checkpoint's embedder) → GFM reasoning over the KG → top-k docs →
answer generation (→vLLM). Endpoints: =/healthz=, =/retrieve=, =/answer=.
Auth: caller needs =run.invoker=; requests carry a Google ID token (1h
expiry — long extractions need refresh).

** Usage workflow (supply-chain risk / lead generation)
1. Structural layer: register tuples (who co-files with whom, subsidiaries,
   sectors, revenue bands, ABNs).
2. Event layer: crawled news tuples (e.g. VIQ→e24 subcontracting breach,
   auditor relationships) connect onto the same nodes via entity linking.
3. Multi-hop queries G-Reasoner is for: "which insured prospects are ≤2 hops
   from this breached vendor", "which companies share the
   concerns-dismissed-by-management governance signature".
4. Outputs: underwriting risk scores (hop-distance to incidents) and
   lead-gen collateral ("your ecosystem depends on vendor class X…").
5. *Hard gate before anything reaches a prospect:* every claim must trace to
   a verified triple + source register link/URL — asserting a false breach
   about a real company is defamation risk, not a quality bug.

* Quality control — summary of all gates
| Stage | Gate | Achieves |
|-------+------+----------|
| shards | idempotency + row accounting + wart scan | input fidelity, attributable errors |
| extraction | per-doc non-empty; arity rate per rung | structural validity, model regression detection |
| extraction | =verify_tuples.py= vs register ground truth | factual fidelity; catches LLM typos & hallucinated facts |
| extraction | genre golden set (register + news + opinion docs) | catches wrong-binding hallucinations guided decoding can't |
| KG build | entity-resolution spot-checks; orphan-edge scan | graph connectivity for multi-hop |
| KG build | embedder/dim consistency with checkpoint | retrieval correctness |
| serving | =qa_eval.py= hit@k + answer accuracy (gold from CSV) | end-to-end quantitative regression gate |
| serving | grounding: answer cites retrieved docs/links | lead-gen safety (zero unverifiable claims) |
| cost | ladder rungs + ladder-results.md | spend predictability before the big rung |

* Benchmarking methods — determining the best options

** Cost & throughput: the exponential ladder
Disjoint rungs 16/64/256/1024/4096/rest (=corpus-shards/=, seed 42). Per
rung record wall-clock, tokens, GPU-hours × AUD rate, sec/doc and arity rate
(=corpus-tuples/ladder-results.md=). Cost/doc should fall (batching
saturates) then flatten; extrapolate after rung 3; abort if projection
diverges. Rung 0 (local) done: 87 s/doc, 11% arity, A$0.

** Extraction model selection
- Local screening: =deploy/PERFORMANCE_REPORT.md= method — fixed passage,
  entities/triples/structure-quality table (this is what eliminated phi3.5
  and thinking-mode, picked the qwen family, demoted gemma2).
- Cloud A/B: swap =model_id= in tfvars (3B ↔ 7B ↔ AWQ variants), re-run a
  middle rung (256 docs), compare arity rate + verify_tuples pass rate +
  cost/doc. Decision rule: cheapest model whose verified-fact rate matches
  the best.

** Reasoner selection (8M vs 34M)
=scripts/qa_eval.py --label 8M= / =--label 34M= against the same shard index:
generates questions from the register CSV (gold answers free), scores
retrieval hit@k and answer accuracy per checkpoint. Add multi-hop questions
derived from =RelatedStatements= chains — that's where the 34M should
separate from the 8M. Labelled outputs make the comparison reproducible.

** Embedding A/B
For the 34M path: Qwen3-Embedding-0.6B (pinned) vs larger Qwen3-Embedding-8B
for query-side encoding — same qa_eval harness, watch hit@k vs GPU memory/
latency cost.

** Upstream benchmark harness
=scripts/gfm-rag/= and =scripts/g-reasoner/= (stage1 index → stage2
pretrain/finetune/evaluate → stage3 QA + IRCOT inference) plus
=scripts/graphrag_benchmark_evaluation/= reproduce the paper's HotpotQA /
MuSiQue / 2WikiMultihopQA numbers — the sanity check that our deployment of
the checkpoints performs at published levels before trusting domain results,
and the path to fine-tuning a register-domain checkpoint later.
