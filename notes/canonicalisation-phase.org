#+AUTHOR: eugene

#+STARTUP: overview

* Why this is its own phase

The GFM-RAG pipeline today has two phases:

- *Stage-1* — OpenIE + NER over each document → ~per-shard ~tuples
  (=nodes.csv=, =edges.csv=, =relations.csv=). One node per *surface form*
  that the extractor saw.
- *Stage-2* — embed nodes/relations (Qwen3-0.6B) + build the reasoning
  =graph.pt= and the ColBERT entity-linking index.

Neither phase knows that "Nick Scali Ltd", "Nick Scali Limited", and
"NICK SCALI LIMITED" are the *same legal entity*. Stage-1 emits a distinct
node for each surface form because OpenIE works per-document and never
reconciles across documents. Stage-2 then embeds those near-duplicates as
distinct points, and the union merge across shards multiplies the problem:
the same company filed in shard-0 and shard-3 becomes two nodes joined only
by a cosine =equivalent= edge.

This is the classic *Entity Resolution / master-data* problem. It is a
recognised, named stage in every production knowledge-graph and
data-integration system — not an optional clean-up. It belongs *between*
stage-1 and stage-2:

#+begin_example
  extract (stage-1)  →  CANONICALISE (this phase)  →  embed + graph (stage-2)
#+end_example

* Why it must be periodic (not one-shot)

The project's purpose is a *continuously-crawled* supply-chain index: each
ABN gets enriched with supplier data over time, and new Register filings
arrive. That is an *increment–compact* cycle:

- *Increment* (per crawl batch) — resolve only the new/changed entities
  against the existing canonical store. Cheap, incremental, runs on every
  ingest. Catches the easy cases (exact ABN match, exact name match).
- *Compact* (periodic, e.g. nightly/weekly full reconciliation) — re-resolve
  the *whole* corpus. Catches cross-batch duplicates that incremental missed,
  re-evaluates fuzzy/blocked candidate pairs with the now-larger context, and
  re-stamps stable canonical IDs. This is the "compact" half — analogous to
  LSM-tree compaction or a vacuum: amortised, idempotent, restores order.

A crawler that never compacts accumulates duplicate drift; one that only
ever does full reconciliation can't keep up with ingest latency. You need
both. Canonicalisation is therefore *a job in its own right that runs on a
schedule*, not a step you run once.

* The deterministic key: ABN

Every reporting entity on the Modern Slavery Register has an *Australian
Business Number* — an 11-digit government-issued identifier. This is a
*deterministic canonical key*: two surface forms with the same valid ABN are
the same legal entity, full stop. No fuzzy matching, no threshold, no
embedding similarity. This is the strongest possible signal and we exploit
it first.

Stage-1 already extracts ABNs as edges:

#+begin_example
  nick scali limited,has abn,82 000 403 896,{}
  plush think sofas pty ltd,has abn,55 080 012 595,{}
#+end_example

Normalisation: strip spaces/punctuation → 11 digits. Reject malformed ABNs
(e.g. =regional express holdings limited,has abn,3878= — 4 digits, an OpenIE
extraction error) — they must NOT seed a merge.

* The critical distinction: MERGE vs LINK

This is the rule that prevents canonicalisation from destroying information:

- *Same ABN → MERGE.* Different surface forms, one ABN ⇒ one legal entity.
  Collapse to a single canonical node; remap every edge onto it.

- *Same corporate group, different ABN → LINK, do NOT merge.* A parent and
  its subsidiary each have their own ABN. "Nick Scali Limited" (the group
  filer) and "Plush-Think Sofas Pty Ltd" (covered entity) are *distinct legal
  entities* that happen to share a modern-slavery statement. Merging them
  would erase the supply-chain structure we are trying to build. Instead,
  add an explicit relation (=group_member_of= / =covered_by_statement_of=)
  and keep both nodes.

For the supply-chain mission this distinction *is* the product: we want the
corporate-family graph, not a flattened blob. Merge removes noise; link adds
the signal.

* Canonical entity store

A persisted table (bucket JSON / Firestore), keyed by canonical ID, holding:

| field            | meaning                                             |
|------------------+-----------------------------------------------------|
| =canonical_id=   | stable surrogate key (e.g. =abn:82000403896=)       |
| =abn=            | normalised 11-digit ABN (null if none extracted)    |
| =canonical_name= | chosen display name (longest/most-frequent variant) |
| =aliases=        | every surface form that resolved here               |
| =first_seen=     | crawl batch / date                                  |
| =last_seen=      | crawl batch / date                                  |
| =source_docs=    | statements mentioning this entity                   |

Stability matters: once an entity has a =canonical_id=, later crawls must
reuse it so downstream crawler state (supplier enrichments keyed by ID)
survives re-reconciliation. The ABN makes the ID naturally stable
(=abn:<digits>=); entities with no ABN get a content-hash surrogate that is
re-checked on compact.

This store *replaces* the broken cosine =equivalent=-edge augmentation
diagnosed in the union A/B: 81% of union edges were =equivalent= synonym
links that flooded entity retrieval with near-duplicates and over-smoothed
the GNN. Deterministic ABN merge removes the duplicates at the source
instead of papering over them with similarity edges.

* Phase-0 prototype (this commit)

Scope deliberately minimal — the *deterministic ABN-merge* slice only:

1. Load union-0-5 stage-1 CSVs.
2. Build =abn → {surface forms}= from =has abn= / =abn= edges
   (normalised, valid 11-digit only).
3. For each ABN with >1 surface form, choose a canonical name and map every
   variant → canonical.
4. Remap =source= and =target= of every edge through the map; drop
   self-loops and exact-duplicate edges created by the collapse.
5. Rewrite nodes.csv (collapsed) and edges.csv to a NEW dataset
   =union-0-5-canon= (leaves =union-0-5= intact and revertable).
6. Report collapse stats (entities merged, edges deduped).

Explicitly *out of scope* for Phase-0 (later phases):

- Fuzzy / blocked matching for entities with no ABN.
- The MERGE-vs-LINK *link* side (adding =group_member_of= edges) — Phase-0
  only does the safe MERGE side.
- The persisted canonical store + stable-ID lifecycle.
- Incremental resolution against an existing store.

* Validation

After rebuilding stage-2 on =union-0-5-canon=, re-run the relational A/B
(=tmp/run_ab_relational.py=) on the entity-retrieval queries that currently
fail (iiNet co-filers, Rex group, Nick Scali → Plush, RAC group). Success =
entity retrieval surfaces the right corporate-family members instead of
=the trustee for think tank commerc…= hub noise.

* Metrics & risks

- *Metric* — duplicate-collapse rate (surface forms per ABN), edge dedup
  count, entity-retrieval recall on the A/B set before/after.
- *Risk: bad ABN extraction.* A wrong ABN merges two unrelated companies.
  Mitigation: validate 11 digits + (later) ABN checksum; log every merge for
  audit; merges are reversible because =union-0-5= is preserved.
- *Risk: over-merging group members.* Mitigated by the MERGE-vs-LINK rule —
  Phase-0 only merges on *identical* ABN, never on shared statement.
- *Risk: canonical-name churn* across reconciliations destabilising IDs.
  Mitigated by keying IDs on ABN, not on the display name.

* Ties to the increment–compact cycle

This phase is the *compact* operator for entity identity. The crawler's
per-batch ingest is the *increment*. Running full canonicalisation on a
schedule (the periodic job the question asked about) is exactly the
compaction that keeps the supply-chain index from drifting as it grows.
