* Why it's viable (the core findings)

- *Minted graphs are tiny and shippable.* shard-0 =graph.pt= is 896 KB; a full
  17k-doc index is tens of MB. The big artifacts (34M=133MB, Qwen3-Embedding-
  0.6B ~1.2GB, ColBERT 419MB, mpnet 440MB) download ONCE. So "download a fresh
  graph" = sync a few MB.
- *Latency is LLM-bound, not graph-bound.* The retrieve path is six lines
  (=gfmrag_retriever.py:150=): =ner_model(query)= (slow, local LLM) → ColBERT
  EL → node2id lookup → =text_emb_model.encode= → GFM forward. Everything
  except the NER call is sub-second; the GFM GNN forward scales ~linearly with
  edges but stays sub-second to a few seconds even at shard-4. Graph size 16 →
  4096 docs adds only a few seconds.
- *Decoupled generator.* GFM-RAG is retriever/generator-split. Expose
  =/retrieve= only; let Claude Desktop be the generator. =/answer= (retrieve +
  a *local* answer LLM) is wasted when Claude is already the caller.

* Bottleneck 1 — query-NER (the dominant cost)

Target: the single slow line, =mentioned_entities = self.ner_model(query)=.

** Option A — let Claude do the NER (best; removes the local LLM entirely)
=ner_model= is a =BaseNERModel=. Add a passthrough impl:
#+begin_src python
class PassthroughNERModel(BaseNERModel):
    def __call__(self, query, entities=None):
        return entities or []
#+end_src
MCP tool signature becomes =retrieve(query, entities, top_k)=. Claude already
parses the question; the tool description instructs it to pass the
company/entity names it identifies. *ColBERT still fuzzy-links those names to
real graph nodes*, so Claude needn't know exact register spellings ("Woolworths"
→ "WOOLWORTHS GROUP LIMITED"). The existing =if len==0= fallback (uses the raw
query for linking) covers the empty case. ~15 lines + one tool-description
sentence. Result: retrieve = embed + ColBERT + GFM ≈ sub-second–2s, no local LLM.

** Option B — keep local NER, make it fast
For clients that won't do NER. Either qwen2.5:3b via Ollama on Metal (~1–2s),
or replace the generative NER with classical NER (*GLiNER*/spaCy, ~50ms CPU).
Entity extraction doesn't need a generative model; GLiNER is purpose-built and
a cleaner dep than an LLM.

** Option C — cache
LRU cache on =ner_model(query)= keyed by normalised query; kills cost on
repeated entities. Insurance, not a primary fix.

*Ship A as default tool + B (GLiNER) as the self-contained fallback.*

* Bottleneck 2 — cold start (make it one-time)

- *Persistent MCP server, eager load*: do =GFMRetriever.from_index(...)= at
  server startup (as =app.py= lifespan does), not lazily per tool call.
- *Ship the stage-2 index pre-built*: =from_index= reads an existing stage-2
  dir keyed by a dataset fingerprint; distribute it with the graph → load is
  deserialisation (~6s warm, 8M) not a 4-min embed pass. This IS the concrete
  "download a minted graph": graph.pt + stage-2 embedding dir + node2id/rel2id.
- *Warm the embedder*: dummy =encode(["warmup"])= at startup so the first real
  query doesn't eat lazy CUDA/Metal init.

* Bottleneck 3 — hardware floor (match embedder to device)

The 960M is the problem, not the design (torch 2.8 has no sm_50 → ColBERT
forced to CPU on that box).
- *Apple Silicon*: torch MPS for GFM+embedder, Ollama on Metal. Smoothest
  target; unified memory shares RAM across embedder/ColBERT.
- *Modern NVIDIA (Turing+)*: existing CUDA path; the sm_50 failure disappears.
- *CPU-only*: viable because latency is LLM-bound. GFM forward + mpnet/Qwen3-
  0.6B query encode are fine on CPU (=CUDA_VISIBLE_DEVICES=""=); ~2–4s GFM at
  shard-4. Pair with Option-A NER (no local LLM) → still snappy.

* Bottleneck 4 — resident memory (shrink & share)

- *Default to 8M locally*: validated local winner (2/2 vs 34M 1/2 on shard-0);
  embedder mpnet (440MB) vs 34M's Qwen3-0.6B (~1.2GB). Offer 34M opt-in for
  RAM-rich, multi-hop use.
- *=GFMRAG_EMB_BATCH_SIZE=8=*: bounds embedder peak during any local stage-2
  build (excluded from the dataset fingerprint — changes only peak memory).
- *Option-A NER removes the largest chunk* (no local generative LLM = no 2–5GB
  held). 8M + passthrough NER → resident ≈ mpnet + ColBERT + GFM ≈ 2–3GB;
  comfortable on 16GB alongside Claude Desktop.

* Bottleneck 5 — multi-graph (merge or parameterize)

Our 4 shards are *separate* graphs today → cross-shard questions unanswerable.
- *Preferred: merge into one index.* Shards are disjoint by construction
  (ladder cut), so concatenate documents and run one stage-1+stage-2 over the
  union. EL then connects the same company across former shards into one node —
  exactly what enables cross-shard multi-hop. Full 17k as one graph is still a
  small index.
- *Alternative: a =graph= parameter* on the tool, multiple retrievers routed by
  arg. More complex; DEFEATS cross-shard reasoning — only justified if the
  shards are genuinely different corpora (register vs news) queried separately.

* Recommended viable stack

Merged single graph (5) + pre-built shipped index (2) + 8M checkpoint (4) +
passthrough NER with Claude doing extraction (1) + CPU-or-Metal (3).
→ *No local LLM, ~2–3GB resident, one-time ~10s load, sub-second–~2s retrieve.*
Claude Desktop is the generator; the local machine only does the cheap,
deterministic graph reasoning the GFM is good at.
