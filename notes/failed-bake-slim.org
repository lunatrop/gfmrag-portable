A negative result, recorded so it isn't blindly retried. The attempt to persist
the extractor job's fixed overheads by (1) pre-baking the ColBERT CUDA

* Goal

gfmrag-extract is a Cloud Run *Job* — instances tear down on completion, so
every run re-pays its fixed startup from scratch. Nothing can be kept "warm"
(Jobs don't reuse instances), so the only ways to cut these are to move work to
build-time (bake) or shrink the artifact (slim).

** The specific overheads we tried to mitigate

Measured on the clean shard-0 run (execution =gfbhj=, 16 docs), per cold run:

| Overhead                         | Measured | Nature                       | Targeted by | Outcome     |
|----------------------------------+----------+------------------------------+-------------+-------------|
| Image load (pull ~18 GB image)   | ~10-13 min | fixed; ~7-8 GB devel base + ~8 GB venv | *slim*     | FAILED      |
| Python imports (torch, faiss)    | ~5 min   | fresh-process; per cold run  | (neither)   | not addressed |
| ColBERT CUDA JIT compile         | ~84 s    | fixed; per-instance ephemeral | *bake*     | FAILED      |
| (vLLM cold start, shared dep)    | ~167 s   | Service, not the Job         | (warm vLLM) | out of scope |

Notes: the JIT figure is the =decompress_residuals_cpp= compile
(12:35:46 -> 12:37:10 in the gfbhj log); =packbits_cpp= + PLAID build add ~57 s
more, so the full entity-linking setup is ~140 s of which the JIT is the bulk.
Python imports are NOT addressable by bake or slim — only a warm process (a
Service, not a Job) avoids re-importing torch/faiss each run.

** The plan

1. *Bake* — pre-compile decompress_residuals_cpp / packbits_cpp at =docker build=
   time (=bake_extensions.py=, TORCH_CUDA_ARCH_LIST=8.9 to target the L4 without
   a GPU on the builder), so runtime skips the ~84 s JIT. (Targets the JIT row.)
2. *Slim* — once nvcc is no longer needed at runtime, ship on
   =nvidia/cuda:12.6.3-runtime-ubuntu24.04= (multi-stage) instead of the ~7-8 GB
   *devel* base, shrinking the image and the ~10-13 min load. (Targets the image
   row — and depends on the bake having removed the runtime need for nvcc.)

* What happened

- The build *succeeded* — =bake_extensions.py= produced a =.so= (its
  fail-if-no-.so guard passed), so the bake "worked" at build time.
- The runtime *failed*. On the slim base, the entity-linking phase tried to
  *recompile* the extension:
  =load() -> _write_ninja_file_and_build_library -> _run_ninja_build ->
  CalledProcessError=. The slim base has no nvcc/ninja, so the recompile
  hard-failed and the job died at =el_model.index= (exit 1, execution 96zs7).

* Root cause

The baked =.so= was not found / not used by ColBERT's loader at runtime, so it
fell back to compiling — which the slim base cannot do. Two compounding reasons:

1. *Build-without-GPU tagging / path mismatch.* torch's cpp_extension cache is
   keyed by a build directory whose name/hash depends on the build environment.
   A GPU-less Cloud Build worker tags/locates the extension differently from the
   GPU runtime instance, so the runtime recomputes a path that misses the baked
   artifact. (pylate/ColBERT also appear to use their own =build_directory=
   rather than honouring =TORCH_EXTENSIONS_DIR=, so the bake's output location
   and the runtime's lookup location may simply differ.)
2. *No graceful fallback after slimming.* Removing nvcc/ninja to slim the image
   means a cache MISS cannot recover — it goes from "recompile 84 s" to "hard
   fail". Slimming and runtime-JIT are mutually exclusive.

* Lessons

- *Don't slim off the toolchain while the extension is JIT-compiled at runtime.*
  The two are coupled: slim base REQUIRES a guaranteed-hit baked/cached
  extension; if the hit isn't guaranteed, keep the devel base.
- *Baking GPU extensions without a GPU at build is unreliable* for this loader —
  the build-vs-runtime cache key/path differs.
- A successful =docker build= does NOT prove the bake is *used* at runtime —
  validate by running the job and confirming no recompile, not by build success.

* What would actually work (future options)

1. *GCS-mounted torch_extensions cache* (lower risk, keeps devel base):
   set the extension cache dir to a path on the already-mounted hf-cache bucket;
   the FIRST GPU run compiles to GCS (~84 s), every later run hits the cache and
   skips it. Needs ColBERT to use a configurable =build_directory= pointing at
   the mount. Persists the JIT without a build-time GPU; image stays full-size.
   Seedable from the persisted =openie_checkpoint.jsonl=-style per-run caches.
2. *GPU-equipped builder*: compile the extension on a machine with an L4 so the
   tag/path matches runtime, then slim. Cloud Build has no GPU — needs a custom
   GCE build runner. More infra, but unlocks both bake AND slim.

* Net

- JIT (~84 s): persistable via option 1 (GCS cache) — *TODO*, not done.
- Image load (~10-13 min, the bigger cost): only persistable by slimming, which
  needs a working bake (option 2) — *not pursued*.
- For now the durable levers remain (CAMPAIGNS.md): *bigger shards* (amortise)
  and *warm vLLM* for a campaign. =bake_extensions.py= is kept in-tree for a
  future option-2 attempt.
