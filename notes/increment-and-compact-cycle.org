#+TITLE: Incremental indexing for a continuously-growing GFM-RAG graph
#+AUTHOR: eugene@tautsec.com (generated with Claude)

#+STARTUP: overview

A design theory for growing the knowledge graph continuously as arbitrary
fact-gated corpora arrive (random crawling), in O(new data) per arrival rather
than O(total graph). The organizing pattern is an *LSM-tree for knowledge
graphs*: cheap appends + periodic compaction.

Status: *theory / design*, not implemented. gfmrag's =kg_constructor= is
batch-only today; this sketches what incremental support would require.

Context: [[file:../pipeline.org][pipeline.org]] (the batch pipeline),
[[file:../FACT GATING FOR PROSE.md][fact gating for prose]] (the admission filter),
[[file:NLP-sequence.org][NLP-sequence.org]] (per-stage costs/scaling),

* The enabling principle

The GFM (G-Reasoner / ULTRA-NBFNet lineage) is *inductive*: it has no
per-entity learned parameters — it reasons over node/relation *features* (text
embeddings) + graph *structure* supplied at inference (=forward(data,
node_features, relation_representations, query)=; no =nn.Embedding(num_entities)=).

Consequence: *growing the graph is appending data, not retraining a model.* A
larger =graph.pt= is reasoned over by the same checkpoint with zero retraining.
This is the precondition that makes incremental indexing possible at all.

* Method 2 was never the growth mechanism — it's compaction

The earlier "method 2" (rebuild entity-linking + synonym edges + stage-2 over
the whole union) costs O(total accumulated graph) per arrival. For a stream of
crawls that is quadratic-ish in cumulative work — adding the millionth doc costs
~a full rebuild. So method 2 is *not* a continuous-growth strategy.

Reframed: method 2 is the *compaction* step of a log-structured system. The
fast path is incremental appends; method 2 runs periodically to fold them in
and control drift.

* The living index (persistent state, versioned in GCS)

| Structure            | Shape                                    | Growth        |
|----------------------+------------------------------------------+---------------|
| Canonical node table | node_id -> name -> embedding             | monotonic     |
| Relation table       | rel_id -> name -> embedding (+ inverses) | slow, saturates |
| Edge list            | (src_id, rel_id, dst_id, provenance, count) | append-only |
| ColBERT PLAID index  | over node names (entity resolution)      | incremental add |
| ANN index            | over node embeddings (synonym edges)     | incremental add |
| graph.pt             | GFM tensors, *derived* from the above    | append        |

* The per-increment path (the O(new) pipeline)

A fact-gated batch of triples-with-provenance arrives. For each:

1. *Resolve entities against existing nodes* — the heart of it:
   - encode the mention, search the EXISTING PLAID index -> nearest canonical
     nodes;
   - *identifier short-circuit*: if the mention carries an ABN that exact-matches
     an existing node, merge deterministically (no fuzzy matching for anchors);
   - else similarity >= theta -> *merge* to existing node_id; below -> allocate a
     *new* node, append to the table, and =plaid.add_documents([new_name])= —
     incremental add, NOT a rebuild.
2. *Insert edges*: map resolved ids and append. If (src,rel,dst) already exists,
   increment its =count= (this is the cross-source corroboration signal) rather
   than duplicate.
3. *New relations*: rare after warmup; embed + append.
4. *Synonym edges, incremental*: for each NEW node, ANN-search existing node
   embeddings for top-k similar -> add new<->existing synonym edges.
   O(new x log total), never all-pairs.
5. *Append to graph.pt*: add node-feature rows, node2id/rel2id entries, and
   edge_index/edge_type columns. Valid because the GFM consumes features +
   structure at inference — no retraining.

Cost: O(new) everywhere; no re-embedding of existing nodes, no PLAID full
rebuild, no O(total^2) synonym pass.

* The hard core: entity-resolution drift

This is where graph quality lives, and where pure incremental adds degrade:
- *false-merge* collapses two distinct "ABC Pty Ltd" -> silent corruption;
- *false-split* duplicates one entity across crawls -> multi-hop reasoning
  quietly breaks at the seam.

Mitigations:
- *Blocking* — only compare within candidate sets (entity type / shared tokens /
  identifier class); cheap.
- *Three-way decision* — high-confidence auto-merge / ambiguous -> LLM-judge or
  review queue / low -> new node.
- *Structured backbone as anchor* — register entities resolve deterministically
  by ABN; crawled-news entities link TO those stable anchors rather than to each
  other. The identifier is the strongest, cheapest signal.

* The LSM-tree pattern

- *Writes = appends* to a "recent" tier (fast, O(new)).
- *Periodic compaction* = re-resolve entities across a region, dedup, rebuild
  that region's PLAID index, fold into the base — i.e. method 2 on a region, run
  on a schedule or when drift metrics cross a threshold.
- *Serving reads* base + recent tiers.

Fast appends between compactions; bounded drift via compaction; quality
reclaimed periodically. Same trade as an LSM-tree's memtable + SSTable merges.

* Concurrency & serving

- *Single-writer or micro-batch merges*: accumulate fact-gated triples over a
  window (N docs / 1 hour) and merge as one mini-batch — amortises index-add
  overhead, reduces churn from random arrivals.
- *Snapshot isolation*: serving loads a frozen graph.pt version; the writer
  builds the next version and atomically swaps a "current" pointer on
  completion. No torn reads.
- *Retraction*: provenance + tombstones — if a source is later discredited, mark
  its edges dead; compaction reclaims them. (Critical for the defamation-risk
  gate in the prose fact-gating doc.)

* Global invariants

- *Embedder frozen* — every node embedding must share one space (the stage-2
  fingerprint). Changing it = full re-embed = a migration, not an increment.
- *GFM checkpoint frozen* (or upgraded as a separate migration). Inductive => a
  new graph needs no retrain; a new embedder DOES need a re-embed.
- *Relation canonicalisation* (the au-register profile's job) keeps rel2id from
  sprawling as arbitrary prose arrives.

* Cost summary

| Operation          | Naive (method 2 / arrival) | Incremental         |
|--------------------+----------------------------+---------------------|
| OpenIE             | O(new)                     | O(new)              |
| Entity resolution  | O(total) rebuild           | O(new x log total)  |
| Synonym edges      | O(total^2)                 | O(new x log total)  |
| graph.pt           | O(total) rebuild           | O(new) append       |
| Per-arrival total  | *O(total)*                 | *O(new)* + periodic O(total) compaction |

* What it would take to build

Two pieces of real engineering:
1. Wire ColBERT PLAID =add_documents= + a graph.pt *append* path + new-node-only
   synonym edges into gfmrag's batch-only =kg_constructor=.
2. The entity-resolution *decision policy* (blocking + thresholds + judge/queue +
   identifier anchors) — where the quality risk concentrates.

Everything else (extraction, fact gating, the frozen embedder/checkpoint, the
serving path) is already in place from the batch pipeline.
