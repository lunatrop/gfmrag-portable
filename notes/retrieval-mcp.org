* Why these defaults
- *Documents by default, entities on request*: not just preference — GNN
  *entity* retrieval is degree-bias-broken (memory: retrieval-path-decision);
  document retrieval + edge traversal is the trustworthy path. Entity mode must
  carry a "known-degraded" note in its tool description.
- *Flat AND graph*: the A/B (corpus-tuples/union-0-5-eval) showed flat beating
  graph on broad sector queries; graph is for true multi-hop. Exposing both lets
  the caller (and future evals) choose per query.

* Tool surface
** Retrieval
- =gfm_retrieve(query, mode="graph", target_type="document", top_k=8, entities=[])=
  - =target_type= default ="document"=; ="entity"= only if explicitly asked
    (degraded-path warning in description).
  - =mode=: ="graph"= (GFM-RAG) | ="flat"= (cosine baseline). Both server-side.
  - =entities=: optional passthrough — Claude supplies the org names it finds;
    lets graph mode skip the vLLM NER call (no vLLM warm needed). Empty list ->
    graph mode falls back to raw-query EL (degraded) — see open decision 3.
** Lifecycle (restricted — spends money)
- =gfm_service_up()=    — scale warm + block-until-ready (multi-minute; see below)
- =gfm_service_down()=  — scale to zero (stop paying)
- =gfm_service_status()=— instance + /ready state + live A$/hr accruing estimate

* Service-side changes (small, deploy/serve/app.py)
The service already loads =graph.pt= into memory for graph mode, so flat is
nearly free to add (no new state, no extra cold-start cost):
- Add =mode= and =target_type= to the =Query= model; default
  =target_types=["document"]=.
- *Graph mode*: existing path, unchanged.
- *Flat mode*: port =flat()= from =scripts/eval/run_ab.py= into the service —
  cosine of the query embedding (reuses the already-loaded Qwen3-Embedding-0.6B)
  against =g["x"][doc_ids]= (already resident). No new download/state.
- Keep =entities= passthrough so graph mode can skip vLLM NER.
- Doing flat SERVER-SIDE (not in the MCP client) keeps team laptops thin — no
  419MB graph.pt + 1.2GB embedder per member; both modes hit the one warm pod.

* Lifecycle mechanism + cold-start reality
Levers (already wired):
- Up   = =gcloud run services update gfmrag-qa --min-instances=1= (or a request
         to trigger scale-from-zero).
- Down = =--min-instances=0= (auto scale-down after idle).
- Service: =gfmrag-qa-olbu7sektq-uc.a.run.app=, nvidia-l4, min_instance_count=0.

*"Started" != "ready".* Per scripts/warm_qa.sh, warm-up is THREE layers:
  1. instance up (scale-from-zero)
  2. models loaded — poll =/openapi.json= == 200 (NOT /healthz — CR layer 404s it)
  3. first-query lazy init — ColBERT PLAID build + first GPU embedding pass;
     on the UNION graph this is *~14-18 min* before steady-state ~1s.
So =gfm_service_up= must: set min-instances=1 -> poll =/ready=
(app reports state: loading|warming|ready) -> call =/warmup= -> return only when
=ready:true=, surfacing elapsed time. It MUST warn this is multi-minute.

*Two IAM tiers* (lifecycle spends money):
- =roles/run.invoker= -> broad: anyone who can query (already granted to
  benchmark_caller + extra invokers in qa_service.tf).
- =roles/run.services.update= -> restricted: only those allowed to start/stop.
  Retrieval tools don't need it; lifecycle tools do. Don't hand everyone the
  spending lever.

* Cost of a warm service for testing
Repo working rate: L4 Cloud Run ~ *A$1.2-1.6/hr active* (midpoint A$1.4).
| Config | A$/hr warm | When |
|--------+------------+------|
| QA pod only (flat + graph, passthrough-NER) [recommended] | ~A$1.4 | no vLLM |
| QA pod + vLLM warm (LLM-NER mode) | ~A$2.8 | only if testing server-side NER |
| Scaled to zero (idle) | ~A$0 (storage cents) | between sessions |
- 2-3 hr session ~ *A$3-5*; full day warm ~ *A$34*.
- The ~15-min warm-up is BILLED before the service is usable -> don't cycle
  up/down repeatedly (each cycle re-pays the ColBERT rebuild). Pattern: =up=
  once -> test the session -> =down=. The status tool's live A$/hr enforces this.
- Flat costs the same as graph (same pod) -> A/B both modes in one warm session
  at no extra cost.

2. *Flat-mode embedder*: flat reuses the 34M's Qwen3-0.6B query encoder already

* Local variant (Shape C) — per-session requirements
Each member's machine becomes the retriever (loads the index in-process)
instead of proxying to Cloud Run. Maps to notes/local-gfm.org Shape C.

** Download once
- *Index from GCS (~0.5-1GB, union):* the WHOLE processed dataset dir, not just
  graph.pt — =stage2/<fingerprint>/{graph.pt,node2id.json,rel2id.json}= +
  =stage1/= (nodes/edges/relations + documents, read for node attributes/text).
  =gsutil -m cp -r= from the bucket (members need bucket read, or a zip/signed
  URL). Never in git (large binary — LFS lesson).
- *Models from HF (cached ~/.cache/huggingface), pinned by checkpoint:*
  - 8M path (~1.3GB): GFM-RAG-8M + all-mpnet-base-v2 (768d) + ColBERT v2
  - 34M path (~1.9GB): G-reasoner-34M + Qwen3-Embedding-0.6B (1024d) + ColBERT v2
  Embedder MUST match the checkpoint (mismatch = silent garbage). See
  big-local-downloads.org.
- *Query-NER:* passthrough (Claude supplies entities — no local LLM, RECOMMENDED)
  OR local Ollama qwen2.5:3b (~1.9GB) for a self-contained server.

** Environment
- Python 3.12 + the full gfmrag venv (=poetry install=): torch, faiss(-cpu),
  transformers, pylate/ColBERT, sentence-transformers — *~5-8GB venv*. This is
  the heavy part. No vLLM, no auth, no per-hour billing.
- gcloud only for the one-time index download.

** Local-mode MCP server (needs building — committed one is a proxy)
Load =GFMRetriever.from_index= in-process at startup (as deploy/serve/app.py
lifespan does), same tool surface, no =_token()=/=_post()=. .mcp.json points at
it with env for index path, checkpoint, NER mode.

** Footprint per machine
- Disk ~7-11GB (venv 5-8 + models 1.3-1.9 + index 0.5-1).
- RAM ~3-6GB resident (+~2GB if local Ollama NER).
- CPU viable (latency is NER-bound; passthrough removes it). Old GPUs (sm_50)
  forced to CPU anyway.

** Two real frictions
1. *ColBERT cold build*: PLAID index over 67k union entities rebuilds each start
   (~14-18min), ephemeral /tmp by default. MUST persist it to a real dir or every
   session launch eats ~15min (serve image uses a writable cache + shutil).
2. *Stage-2 must be shipped pre-built*, not rebuilt (rebuild is OOM-prone/slow;
   needs GFMRAG_EMB_BATCH_SIZE low).
The local path is only pleasant WITH passthrough NER + a persisted ColBERT index
(then ~10s to ready, sub-second-to-few-seconds/query).

* Specialised distribution repo: =tautsec-gfm-service=
A dedicated, team-facing repo separate from the gfm-rag engine/research repo.
*Default = small cloud-service client; fully-local = advanced opt-in.*

** Why a separate repo
The gfm-rag repo is the engine (extraction, training, deploy/ infra, build
pipeline) — large, with the full torch/faiss stack. Team members consuming the
service should NOT clone that. tautsec-gfm-service is the thin consumption layer.
Clean TautSec service-boundary split: engine vs client.

** Default contents (cloud-client — tiny, ~KB-scale clone)
The proxy imports NO gfmrag/torch — it's pure HTTP + gcloud. So default deps are
near-zero:
- =scripts/mcp/gfmrag_server.py= (the proxy: /retrieve, /answer, /ready; mints
  ID token via gcloud).
- =.mcp.json= template (Claude Code) + claude_desktop_config snippet.
- =requirements.txt= = just =mcp= (gcloud CLI assumed present).
- README: gcloud auth + run.invoker grant + how to open in Claude Code.
Clone -> gcloud auth -> done. No models, no heavy venv, no per-hour cost beyond
the shared service.

** Advanced (fully-local) — opt-in extra, NOT default
Behind an optional install (e.g. =pip install .[local]=) so the default clone
stays thin. Adds:
- Local-mode MCP server (loads GFMRetriever in-process).
- Index download script (=gsutil -m cp -r= the processed union dir from GCS).
- HF model download helper (checkpoint + pinned embedder + ColBERT).
- ColBERT-index persistence config; passthrough-NER default (Ollama optional).
- The heavy dependency group: the =gfmrag= package (=pip install gfmrag @
  git+<gfm-rag repo>= or a published wheel) which pulls torch/faiss/pylate.
The =gfmrag= engine stays a DEPENDENCY of the [local] extra, not vendored.

** What the repo must NEVER contain
- graph.pt, models, ColBERT indexes — large binaries, downloaded from GCS/HF at
  setup, never committed (LFS lesson).
- Secrets — ship config templates (service URL, SA/audience) not credentials.
Repo holds CODE + CONFIG + DOWNLOAD SCRIPTS only.

** Compatibility pinning (critical)
The index is checkpoint+embedder+version pinned. A repo release MUST declare
which checkpoint / embedder / index version (and bucket path) it expects, so a
local install matches the deployed service and members don't load a mismatched
graph. Treat index version as a release coordinate.
